# V3 — núcleo de entrada, editor e persistência

Documento técnico do código implementado nesta árvore. Nada aqui depende de Intel/AMD/NVIDIA, resolução fixa, IP, caminho de dispositivo, nome evdev, compositor específico ou Máquina B.

## 1. Fronteiras

| Camada | Módulo | Responsabilidade | Não faz |
| --- | --- | --- | --- |
| Evento | `linuxdroid/input/events.py` | `InputEvent` imutável e predicados | não interpreta perfil |
| Normalização | `linuxdroid/input/normalizer.py` | aliases, tipos, namespaces, evdev→canônico explícito | não converte Qt→evdev |
| Provider | `linuxdroid/input/providers/` | eventos simulados determinísticos | não lê `/dev/input` |
| Backend | `linuxdroid/input/backends/` | gravador em memória e adaptador Phantom passivo | não injeta input real |
| Contatos | `linuxdroid/input/contacts.py` | slots, IDs estáveis, ordem DOWN/MOVE/UP | não conhece Qt |
| Estado | `linuxdroid/input/state.py` | estados, transições e SAFE_RELEASE | não executa comandos |
| Motor | `linuxdroid/input/engine.py` | bindings, camadas, ações lógicas, despacho | não importa PySide6 |
| Runtime | `linuxdroid/input/runtime.py` | orquestra provider→normalizer→engine→backend | não abre hardware |
| Editor puro | `linuxdroid/input/editor_model.py` | histórico, conflitos, dirty state | não desenha widgets |
| Ponte Qt | `linuxdroid/input/qt_bridge.py` | códigos Qt→nomes canônicos | não usa `event.text().upper()` |
| Persistência | `linuxdroid/storage.py` | V2 atômico, backup, V1 legado | não apaga perfil antigo |
| Diagnóstico | `linuxdroid/input/diagnostics.py` | contadores, modos, erros sem texto | não afirma injeção |

## 2. Identidade e proveniência

`InputBinding.provenance` é obrigatório e distintivo:

- `validated_by_vocabulary`: nome reconhecido. Não prova captura.
- `captured_from_device`: captura física declarada por backend com evidência.
- `validated_by_backend`: validação por backend, sem implicar captura global.
- `unverified`:origem desconhecida.

`InputBinding.from_canonical()` usa `validated_by_vocabulary` por padrão. `from_legacy_text()` preserva `unverified`. Nenhum nome aceito é promovido a captura física.

Códigos são sempre acompanhados de `code_space`:

- `evdev`: convertido por tabela explícita.
- `qt_native_scan_code`, `qt_virtual_key`: preservados, nunca convertidos para evdev.
- `unknown`: sem conversão.

## 3. Fluxo do runtime

1. `SimulatedInputProvider` produz eventos com IDs e timestamps determinísticos.
2. `Normalizer` valida/normaliza cada evento.
3. `MappingEngine.resolve()` indexa bindings por identidade canônica + modificadores.
4. A máquina de estados aplica transições de segurança (foco perdido, desconexão, exceção).
5. O motor emite comandos touch com slot e coordenadas normalizadas.
6. `ContactManager` aplica DOWN/MOVE/UP antes de chamar o backend.
7. `RecordingTouchBackend` registra os comandos em memória com `mode="recording_only_no_injection"`.

O diagnóstico resultante usa `recording_backend` quando o backend é gravador, mesmo que o provider seja simulado. `simulation` é reservado para execução sem backend de saída.

## 4. Regras de multitouch

- slots `0..254`; `255` é reservado;
- limite de 10 contatos simultâneos por referência Phantom;
- mesmo `contact_id` e slot enquanto o contato estiver ativo;
- DOWN antes de MOVE;
- UP uma única vez;
- nenhum MOVE depois de UP;
- DOWN duplicado é ignorado e contabilizado;
- falha em MOVE/UP/cancel chama `release_all()` no backend antes de descartar o estado local;
- nenhum contato preso após exceção.

## 5. SAFE_RELEASE

`CaptureStateMachine.safe_release(reason, actions)` é prioritário e idempotente. O primeiro chamado devolve `SafeReleaseReport(idempotent=False)`; chamadas seguintes devolvem `idempotent=True` sem repetir ações. São liberados: contatos, mira, menu touch, captura virtual, captura física conhecida e filas pendentes. Motivos ficam no diagnóstico: `MANUAL`, `FOCUS_LOST`, `DEVICE_DISCONNECTED`, `EXCEPTION`, `PAUSE`, entre outros.

## 6. Editor e persistência

`ControlsScreen` mantém `self.nodes` como payload legacy usado pelo canvas, mas a fonte da verdade é `BindingEditor.profile` (`ControlProfileV2`). Toda mutação de nó, geometria, binding, parâmetro ou camada passa pelo editor, atualizando histórico e dirty state.

- captura local: `QKeyEvent.key()`, `nativeScanCode()` e `nativeVirtualKey()`; nunca texto digitado;
- drag-to-bind: arrastar item da lista para o canvas reposiciona o controle;
- conflitos: `validate_profile()` com severidade erro/aviso; erros bloqueiam o salvamento;
- Undo/Redo, duplicar, copiar/colar, remover e limpar binding usam o mesmo histórico;
- salvamento grava `controls_v2/<package>.json` atomicamente e atualiza a cópia legada `game_controls.json`;
- JSON corrompido é movido para quarentena `.corrupt` sem destruir o original;
- perfil V1 é lido, mas convertido somente em memória até salvamento explícito.

## 7. Capacidades e Phantom

`assess_backend()` distingue: detectado, dependências, pré-requisitos, disponível, testado, operacional e não suportado. `native` pode ser candidato, mas `functional` e `operational` exigem evidência explícita.

`PhantomAdapter` usa allowlist de comandos e runner injetado. Sem runner, nenhum comando é executado. Mesmo com runner, o adaptador reporta `functional=False`, `tested=False`, `operational=False`.

## 8. Limites atuais

- sem captura evdev real, EVIOCGRAB ou leitura de dispositivos;
- sem injeção Android, adb shell input, uinput ou daemon Phantom;
- sem execução de Free Fire, testes competitivos ou anti-cheat;
- sem medição de GPU/FPS/temperatura em Máquina B;
- resolução da superfície Android continua desconhecida até medição autorizada;
- Macro é apenas compatibilidade de dados; runtime automatizado não foi implementado;
- o Python do sistema não possui PySide6; o `.venv` do projeto possui. Por isso os dois testes de integração da GUI são ignorados no comando padrão e executados quando a suíte roda com `.venv/bin/python`, em modo `offscreen`.
